# 個人迷因資料庫可行性評估

評估日期：2026-11-23。依目前工作樹、唯讀資料庫查詢及測試；未修改應用程式、未部署，保留既有未提交變更。外部方案與 R2 官方來源見 [研究紀錄](personal-meme-research-2026-11-23.md)。

## 結論

適合繼續做個人迷因資料庫。應先提升搜尋與取圖體驗，再提供唯讀 Agent API，最後決定公開部署。現有功能已是可用的本地管理工具，不需要重寫。

使用者 VPS 為 2 核、2 GB RAM、每月 0.5 TB 流量，且有其他服務。尚未取得主機實際 RAM、swap、CPU 與流量基線，因此不能保證共機部署不影響既有服務。優先方案為輕量 Flask 服務＋SQLite＋R2；若已有 PostgreSQL 且餘裕足夠，再評估共用 PostgreSQL。OCR、縮圖批次與視覺模型整理留在本機。

## 實測現況

| 項目 | 結果 |
|---|---|
| 梗圖 | 1,076 筆：ready 984、ignored 87、needs_review 5 |
| 無標籤 | 986 筆，約 91.6% |
| 待審候選標籤 | 22 筆 |
| 非空台詞 | 1,015 筆 |
| 主 SQLite | 1,576,960 bytes，約 1.58 MB |
| 附件 | 1,076 個檔案，1,248,484,265 bytes，約 1.25 GB |
| 縮圖 | 1,070 個檔案，11,998,952 bytes，約 12 MB |

附件資料夾盤點不是逐檔完整性驗證。縮圖較少不必然代表錯誤：動態媒體有跳過規則。

現有搜尋只對作品、說話者、台詞、OCR 做整段 LIKE；一般搜尋不查標籤與備註。標籤是獨立精確篩選，排序以更新時間等為主，沒有相關度。以現行預設 ready 範圍查詢「復活」「復活！」「烈海王」「復活 烈海王」均為零筆。這不證明圖片不存在，可能是描述不足或未收錄。查詢本機單次約 0.85–1.84 ms，僅作目前小資料量參考，不代表 VPS 或 HTTP 負載表現。

## 建議搜尋與 UI

1. 補梗名、角色別名、使用情境與同義詞；例如復活、復出、回來了，並保留人工審核。先用 20–30 個自己常用查詢與期望圖片驗收。
2. 搜尋涵蓋正式標籤、描述；正規化全半形與標點、繁簡，支援多詞跨欄位命中，加入相關度排序。
3. 首頁集中搜尋與結果；新增、缺圖、待審核等移至管理模式。狀態改成易懂中文，補待審核獨立篩選。
4. 卡片加入取圖操作、複製圖片或連結、下載；目前主要只有複製台詞與開啟原圖。改善手機搜尋、空結果提示、懶載入及 GIF 靜態預覽。
5. 仍常找不到時才評估混合語意搜尋。不要假定向量模型能辨認特定作品梗；應以驗收查詢衡量。

UI 判斷依 HTML/CSS/JS 與互動流程檢查，本次未做瀏覽器視覺驗收。

## API 與公開邊界

已有 GET /api/entries?q=...、GET /api/entries/<key>，可延伸為穩定唯讀接口；目前未實作 MCP。建議 Agent 工具僅 search_memes(query, limit)、get_meme(id)，回傳少量標題、標籤、預覽與原圖 URL，圖片按需取用。模型推論在呼叫端執行，MCP 本身不要求 VPS 執行模型。

公開前需實作管理員驗證、伺服器端讀寫權限、API token 或適當存取控制、速率及回傳大小限制。現有 Origin 檢查不是身分驗證；收藏也是全域共用，不能直接變成所有訪客可寫。應另定公開輸出欄位，避免直接輸出現有 e.*、本地檔案路徑、內部 notes、來源訊息識別等資訊。

目前使用 app.run 開發伺服器；正式部署需生產 WSGI 服務。Flask 官方：[Deploying to Production](https://flask.palletsprojects.com/en/stable/deploying/)。私人 Tunnel 也需 Access 等驗證，隧道本身不代表私人權限。

## 資源與流量估算

以下為部署規劃預算，並非 VPS 實測：輕量 Web＋SQLite 先預留約 150–350 MB RAM；加入小型 PostgreSQL 後整組先按約 400–800 MB 規劃，實際受 worker、連線數、快取和工作負載影響。2 GB 共機宜先確認持續可用記憶體至少約 500–700 MB 再試輕量版，並觀察尖峰及 swap；這不是保證門檻。

依現有平均檔案大小粗算：一頁 48 張縮圖約 0.54 MB，48 張原圖約 56 MB。每日 1,000 頁、30 天約為 16 GB 縮圖或 1.67 TB 原圖，尚未含點擊、HTML、JSON、重試與快取差異。若圖片經 VPS 回傳，原圖可能快速超過 0.5 TB。

正確分流是使用者或 Agent 直接從 R2 自訂媒體網域取圖，VPS 只回 HTML/JSON/圖片 URL。API 回傳每次假設 20 KB，十萬次約 2 GB；這是計算範例，不是目前 API 實測。不要由 VPS 代理下載 R2 圖片後再轉送。

目前完整附件＋縮圖約 1.26 GB；以相同平均大小推估一萬張約 11.7 GB、十萬張約 117 GB。R2 標準儲存以每月平均容量及操作數計費，免費 egress 不等於無限免費操作；價格與限制見研究紀錄。

## 本地、VPS 與開源

R2 目前只有資料庫預留欄位，Web 尚未接上；SQLite 存取分布多處，PostgreSQL 不是換連線字串即可。需整理資料存取介面、處理 SQL 方言及遷移驗證，並提供 local/R2 儲存模式。

先選單一主資料來源，避免本地和雲端同時編輯衝突。可讓本機管理與批次處理，再發布唯讀雲端快照；或 VPS 為主，本機定期保存資料庫匯出與原圖。備份包含資料、圖片及設定並實測還原；鏡像刪除不能取代備份。若本地也要可獨立運作，這比只有下載備份多一層資料格式與路徑相容工作。

開源自建仍需最小安裝依賴、設定範例、授權檔、可重現部署與還原說明。目前主 requirements 混有 GPU/OCR 大量依賴，不適合直接完整安裝到 2 GB VPS。公開程式碼與公開全部館藏應分開決定。

## 建議順序與驗收

1. 搜尋與 UI：常用查詢可在前五筆找到目標，手機能快速取圖。
2. 唯讀 API：Agent 能完成搜尋及取圖，權限阻擋任何寫入，回傳有限筆數。
3. 私人部署：取得 VPS 基線，接 R2、登入、備份；以實際使用量觀察 RSS、延遲及流量，確認不影響現有服務。
4. 公開唯讀：資料公開欄位、限流、媒體快取確認後再開放；PostgreSQL 與向量搜尋依測量需求加入。
